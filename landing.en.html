Japan's job hunt runs on essays.
This is where they live.

Japanese students apply to dozens of companies at once, and each one asks for an “entry sheet” — a set of open-ended essays, a few hundred to a thousand characters each, every one with its own deadline. ESM keeps all of them in a single screen, with no ads and nothing blinking for attention.

Why I built it

The tools existed.
They were the problem.

01

Writing was the easy part

The hard part was holding everything in your head at once: what you already wrote for four other companies, which deadline is closest, whether this firm rejected you before the interview or after.

02

So it lived in six places

Drafts in a docs app, deadlines in a spreadsheet, character counts in a free web counter covered in ads, company logins in a notes file. Every switch cost attention I did not have.

03

The services meant to help made it worse

The existing job-hunting platforms are free because they sell your attention. Banner ads, push notifications, recommended listings. I burned out on them, and built the opposite.

North Star

“Everything for the job hunt, in one place, without stealing your focus.” Every feature proposal gets one question: does it remove a real friction in the workflow, or is it a feature for its own sake? The second half of that sentence is what kills most ideas — including several of my own, listed further down.

The product

Six things,
done properly

There is no feature list competition here. These are the frictions that actually showed up while applying, and nothing else made the cut.

🗂️
One screen: company → question → draft

A three-level tree. Pick a company in the sidebar, a question inside it, and a draft of that answer. Multiple drafts per question live side by side, so you can rewrite without destroying the version you liked.

☁️
Two independent ways to not lose your work

Every edit is saved to Firestore on a 1.5-second debounce. Separately, the last five generations are kept in browser storage. Cloud and local fail for different reasons, which is the point — one is a backup for the other, not a copy of it.

Reliability
⏰
Deadlines that sort themselves

Any company can carry dated tasks — submit the essay, finish the aptitude test, take the web test. The sidebar reorders itself by whatever is due next, and overdue items sink to the bottom instead of squatting at the top just because their date is oldest.

📚
A material library you assemble from

Your life history, your accomplishments, your self-PR, the core of why you want the job — written once, kept in one place. Company number twelve is assembled from material, not written from an empty page.

⌨️
Operable without touching the mouse

The cursor starts in the essay body. Esc leaves it for navigation mode, arrows move between companies and questions, Enter drops you back into the text. Two bindings that would normally collide, separated by an explicit mode instead of by cleverness.

✨
Claude, inside the drafting flow

Draft from your own material, refine what you wrote, suggest angles you have not tried, or interview you to pull a life history out of you. Streamed token by token through an authenticated proxy — and deliberately built into the existing draft editor rather than bolted on as an “AI tab”.

Architecture

Static page,
serious back end

The frontend is a single HTML file served from GitHub Pages. Everything that needs to be trusted happens somewhere the browser cannot reach.

Client
index.html
2,504 lines of vanilla HTML, CSS and JS. No framework, no bundler, no npm. Served as a static file from GitHub Pages.
│ Google sign-in
Identity
Firebase Auth
Issues the signed ID token that everything downstream checks.
Storage
Cloud Firestore
One document per user: users/{uid}. One read on login, one debounced write to save. Rules allow access only when request.auth.uid == userId.
Local
Browser storage
Five most recent generations, kept independently of the cloud path.
Trust boundary
Cloud Functions ai
Gen 2, Node 20, asia-northeast1. Verifies the ID token, checks the caller against a fail-closed allowlist, then relays to Claude over SSE. CORS restricted to the production origin and localhost.
│ API key from Secret Manager
External
Claude API
Streaming completions, proxied straight back to the browser.

The shape in one sentence: a static page talks to Firestore under owner-only rules, and everything involving a secret is pushed behind a Cloud Function that the client cannot bypass. There is no server to operate and no container to patch.

Engineering decisions

Three calls,
and what I turned down

The choice is only half of a decision. Each of these lists the alternative I rejected and why, because that is where the actual reasoning lives.

01

One HTML file. No bundler, no framework.

WhyThe product's entire premise is that it does not steal your attention, and I wanted the same property in the codebase. At this scale, a build pipeline is maintenance I pay for forever — dependency upgrades, config drift, a CI job to keep green — against value I would never collect. Local development is python3 -m http.server. Deployment is git push.

RejectedReact or Vue on Vite, which is the reflex answer. At 2,500 lines, the bundler's overhead costs more than the component model returns, and node_modules is a security surface I would then have to watch. I would choose differently at 20,000 lines; I would rather be accurate about the size I am actually at than build for the project I imagine having.

02

All of a user's data in a single Firestore document.

WhyThere are exactly two Firestore calls in the whole frontend: one get() on login, and one debounced set() that writes the entire company → question → draft tree at once. A single-document set() is atomic in Firestore, so a partial write is structurally impossible — the tree can never end up half-updated. It also bounds usage at one read per session and at most one write every 1.5 seconds.

RejectedSplitting into companies/{id} and questions/{id} subcollections — the normalized shape a reviewer would expect. Editing one deeply nested field would then mean writing several documents, any of which can fail independently, and I would be writing reconciliation logic to repair states that the single-document design simply cannot enter. The payoff would be query efficiency I do not need at a few dozen companies per user.

03

The browser never touches the Claude API.

WhyA Cloud Function verifies the Firebase ID token, checks the caller against an allowlist, and only then relays the request. The API key exists solely in Secret Manager and is read as an environment variable inside the function. That is three independent layers — secret isolation, identity, authorization — and none of them require the frontend to know anything it could leak.

RejectedCalling Anthropic directly from the browser. This was never genuinely a candidate, but it is the shortcut a prototype reaches for, so it is worth naming: anything in client-side JavaScript is extractable, and an extracted key is a stranger spending my money until I notice.

Security model

What is secret,
and what only looks like it

The repository is public, which forces the question to be answered precisely rather than by instinct.

🔑

The Claude API key is a real secret, and lives in one place

Google Secret Manager, injected into the function's environment at runtime. Never in the client, never in the repository, never in an environment file that could be committed by accident.

🪪

The Firebase apiKey in the client is not a secret

It is a public project identifier — Firebase's own documentation says so. Treating it as secret would be cargo-cult security: it would buy nothing, and it would suggest the real access control lives in hiding that string. It does not. It lives in the Firestore rules and in the function.

🔒

Firestore rules are owner-only, and checked into the repo

allow read, write: if request.auth != null && request.auth.uid == userId. The rules file in the repository is the deployed rule set, pulled from production rather than written from memory, so it cannot quietly drift out of sync with what is live.

🚫

The allowlist fails closed

If the list is unset, empty, or fails to load, everyone is denied — including a caller holding a perfectly valid ID token. An earlier version skipped the check entirely when the list came back empty. I changed it, because “misconfigured, so nobody gets in” is recoverable and “misconfigured, so anybody gets in” is not.

📋

User IDs were externalized too — for a different reason

The allowlist holds real UIDs of two identifiable people, and this repo is public. A UID is not usable without a signed token, so it is not a secret; it went into Secret Manager anyway, to keep one operational path for values that leave the codebase instead of two.

Restraint

What I decided
not to build

A product whose promise is “does not steal your focus” is mostly defined by its refusals. Each of these was designed far enough to be rejected on the merits.

✕Push notifications The exact mechanism I built this to escape
✕Calendar view A second place for dates to disagree with the first
✕“Generate three full drafts” Litters the workspace; one suggested angle beats three finished essays
✕Command palette Discovery cost too high for a tool this small
✕Scroll-to-advance Cheap to build, nobody would ever find it
✕Duplicate-draft button Shipped, then removed — it made more drafts, not better ones

What is next

Company research grounded in web search. The obvious version — asking the model what it knows about a firm — is the wrong one: a knowledge cutoff plus a confident tone is exactly how a student walks into an interview citing something that was never true. If this ships, every claim carries a source and it is framed as reference material, never as fact.
